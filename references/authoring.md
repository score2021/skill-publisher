# 从需求与认可流程到 skill

## 1. 选择来源

只使用当前可见会话、用户明确提供的摘要/文件，或在授权范围内可访问的指定历史记录。不能默认读取所有聊天，也不能扫描整个个人/公司工作区来寻找“成功案例”。先限定与任务有关的材料。

给候选经验标注：

| 分类 | 证据 | 处理 |
| --- | --- | --- |
| 认可 | 用户明确说保留/采用/按此执行，或认可了具体产物 | 保留所指范围内的规则 |
| 已执行 | 工具成功、测试通过，但没有用户评价 | 作为候选方法，不称已获认可 |
| 反对/撤销 | 用户纠正、取消或要求换方案 | 不纳入已认可规则，遵循最新修正 |
| 临时绕路 | 本机权限、缺工具、特定服务故障 | 只有可泛化且有必要才留作条件处理 |

用户说“就按这个方案”可认可该方案，不代表所有后台尝试。只认可一个步骤时不扩大到整次会话。证据缺失时写“未见明确认可”，仍可按当前明确需求提出方法；不编造赞同原话。

在工作记忆或简短摘要里映射“来源依据 → 通用规则 → 测试行为”，不把完整会话打包；确需存摘要时使用脱敏内容，默认放发布目录外。

## 2. 定义最小行为契约

明确：使用者、触发条件、所需输入、预期产物、成功标准、失败/停止行为、外部副作用与授权。复杂技能用几条代表性场景说明即可，不强制独立契约/计划文档。

需求已清楚就继续；只问会改变行为的问题。优先复用已有 creator 工具，缺失时按这里直接编写，不能谎称依赖已加载。

## 3. 编写方法

新建时先区分“未命名/基础名”和“明确要求保留完整名称”，再按主文件的 `z-` 默认规则确定最终调用名，再写目录与元数据。前缀只加一次；旧式下划线输入先转为单连字符，再核对前缀。不能出现目录带前缀而 frontmatter 不带、README 使用旧调用名等不一致。新生成 skill 有 UI metadata 时显式保留带 `z-` 的 display_name，并在 default_prompt 写真实 `$z-…` 调用名。

使用标准 initializer/quick_validate 检查命名及格式，不修改第三方验证器来放行错误。名称应符合 `z-[a-z0-9]+(?:-[a-z0-9]+)*` 且总长不超过 64；目录与 name 一致。格式通过后再验证真实调用；其他客户端仍只声明实际测过的范围。

- description 写实际能力和触发语境，避免泛泛吸引所有任务；仅查某份普通 README 不应触发完整发布流程。
- 主文件只保留执行时总需要的规则和导航。条件细节放 references，并写明什么时候读；不要默认一次读全。
- 用明确动作和短例子解释关键选择，解释必要的原因，避免大量 MUST 或规则重复。
- 保留“为什么以及如何决定”，不复制一场会话的叙事。不以固定语言、库、路径或旧业务名替代通用方法。
- 脚本只处理稳定、重复、可确定检查的部分；先运行并验证正反场景，再加入 skill。
- 不建立无用途的 assets、语言包、索引层或初始化体系。不把外部案例中的自动 push、安装依赖或子代理授权搬过来。
- 修改现有 skill 时保留名称、有效约束和用户定制；新旧版本对比测试，避免不必要重写。

## 4. 保留 PTDD 的交付经验

保留行为先行、按需读取、独立打包、真实环境验收、发布后从用户视角复验。README 从目标用户和实际价值展开。阶段数、中文偏好、许可证、覆盖率和编程语言不能无条件套到所有生成物。

仅生成用户要求的产物。多 skill 默认独立目录，未要求捆绑就不要混装。
