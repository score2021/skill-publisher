# 发布目录与 README

## 发布目录

单 skill 默认以 SKILL.md 为根，保留它引用的必要资源；README、LICENSE、.gitignore 位于同一根目录。多 skill 按用户要求分别打包，不带无关技能或源项目历史。使用明确允许清单复制，不从整个工作区打包后只依赖忽略规则。

按需保留合成 eval、脚本正式测试、必要 fixture 和许可证；运行日志、真实输入数据、原始会话和临时工具不发布。安装时复制运行资源与许可证，不要求安装 README 或 eval。

## 新建 skill 的命名与安装

未指定名称或只给基础名时，按主文件默认使用 `z-` 前缀，例如 `z-release-note-helper`。文件夹、frontmatter name、安装目标与所有 `$z-release-note-helper` 示例一致；不把目录前缀与调用名前缀拆开。可读的 UI 名称也保留 `z-`，便于候选框筛选。

在生成物 README 说明统一采用标准兼容的 `z-` 个人前缀；不再保留下划线命名例外或声称该前缀不符合标准。含前缀总长不超过 64，只用小写字母、数字及单连字符。只声明实际测过的客户端。明确要求保留完整有效名称时尊重用户；默认规则本身不授权迁移已有技能。README 说明默认前缀用于减少个人技能查找候选、区别官方/插件技能，并符合标准，不是官方强制。

## README 必要内容

1. 一句话说明帮谁完成什么。
2. 适用人群、真实场景、输入与输出；每个新 skill 重新判断用户，不统一写成 PM/开发者。
3. 主要流程及关键确认/停止条件；与 SKILL.md 一致，不复制完整规则。
4. 前置条件、实际安装目录、可执行命令和调用示例；明确 shell 命令与对话输入。
5. “样例”一节：至少一个完整、可直接复制的对话代码块，用实际调用名（默认 `$z-…`）加具体需求与合成输入，不用 `xxx`、`<我的需求>` 或缺失文件作为唯一例子；随后说明预期结果、是否保存和必要前置条件。
6. “成果展示”：具体输入及对应成果、来源/验收状态、关键边界；不能仅有功能清单或预期结果。
7. 会影响使用的默认偏好、权限、依赖与成本条件。
8. 实测环境、已通过/未验证范围和限制；不能把 smoke test 写成全覆盖。
9. 目录、许可证与必要来源说明。

只为实际需要添加贡献、安全、版本等其他文档。许可证以用户选择及可用授权为准；不能把第三方受限材料统一改成 MIT，复制外部内容先核对各文件许可证并保留必要声明。

## Codex 安装说明

核对当前官方客户端文档；当前用户级发现路径为 `~/.agents/skills/<name>/`，允许软链接。已有安装可能在 `~/.codex/skills/` 存放文件；先检查目标与软链接，不能重复同名安装或覆盖个人偏好。

本地版本写“进入包含 SKILL.md 的目录”后复制实际资源；仓库未发布时不要给伪造的可用链接。只在用户要求 GitHub 说明时放清晰标注的待替换模板，发布前必须改为实际账户和地址。

安装块使用带引号的路径，拒绝已存在文件、目录或断开的软链接，支持空格和非 ASCII 路径；包含所有运行依赖，不仅复制 SKILL.md。先在临时 HOME 中原样运行、重复安装应停止、校验文件后再推荐。

CLI 的对话里用 `$skill-name`；终端直接 `codex exec` 时用单引号防止 shell 展开 `$`。不是每个 skill 都注册 `/name` 斜杠命令。下一轮尝试调用，列表未刷新再重启。其他客户端未实测就只说明格式兼容，不能承诺安装与行为均正常。

## 首次使用验收

按 README 的下载/本地获取 → 安装 → 打开目标项目 → 调用 → 核对产物原样执行；安装成功与行为成功分开。无工具/权限时列未验证，不换一条隐藏捷径后宣称 README 可用。

## 可直接使用的样例形式

例如生成的技能名为 `z-release-note-helper`，README 可写：

```text
$z-release-note-helper 我的需求是给 PM 和用户写一份发布说明。
变更：列表新增按日期筛选，原有关键词搜索保留；导出前显示待导出条数。
限制：只能导出 CSV。性能提升尚未测试；用户无需迁移。
请直接输出 Markdown，不保存文件、不发送消息。
```

预期结果：用户变化、限制、需要采取的操作；不虚构性能数据。这个请求无需准备本地文件。为每个新 skill 换成其真实任务，不把发布说明示例强套给日报、图片等其他技能。README 安装或调用名变化时同步更新样例，并用真实客户端执行该样例。

## 成果展示的选择与验收

推荐阅读顺序：一句话价值 → 成果展示 → 安装 → 可复制样例 → 流程与边界。每个技能先选一个能体现真实价值的合成案例，不堆截图或建立展示站。样例与成果可以同节或用锚点互链，读者应能把输入和结果对应起来。

文字技能优先用可复制的 Markdown、对照表或完整短成品；开发流程展示契约/计划关键片段与真实测试证据；视觉技能按需放截图和仓库内相对链接。短成果直接展示，长成果可放 examples/ 并链接全文；不能为了展示而要求用户安装展示资产。

展示须标明来源：实际运行（注明客户端/模型及日期）、当前会话自检、人工整理摘录或未执行示意。只有相应证据存在时才写实际运行通过；未执行的示意仍应有“成果展示”，但不能宣称已完成验收。摘录只做明确标注的删节和脱敏，不改写结论、限制或失败结果。不能将单个案例宣传成性能基准、可靠性保证或必然获得 Star；没有对照实验不声称优于无 skill。

验收时实际执行可复制请求，核对产物是否完成任务、关键限制是否保留、调用名与当前发布版本是否一致、展示是否确实来自该次运行，并检查 Markdown 渲染及资源链接。缺少能力或访问条件时列未验证项，不编造结果。所有展示输入、输出、图片和附件同样检查公司代码、内部地址、身份、凭据与客户数据；截图还检查周边标签页、路径和通知。正式合成案例和经审核的成果属于发布资产，执行原始日志与临时安装清理。
